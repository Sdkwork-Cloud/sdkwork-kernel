# SDKWork Agent Business Database Specification

- Version: `0.1.0`
- Domain: `intelligence`
- Capability: `agent-business`
- Scope: Agent metadata CRUD, provider implementation bindings, deployment
  snapshots, skill package marketplace, MCP server marketplace, prompt template
  marketplace, agent knowledge-base/source/document/chunk/index/binding/sync-job
  management, agent memory store/profile/binding/namespace/record/provenance/
  retrieval-index management, status lifecycle, authorization boundary linkage,
  audit facts, and API contract persistence support.

This document defines the `sdkwork-agent-business` database contract baseline.
It follows:

- `specs/DATABASE_SPEC.md`
- `specs/API_SPEC.md`
- `specs/SECURITY_SPEC.md`
- `specs/IAM_SPEC.md`

## 1. Design Principles

1. Every agent-business table uses the `a_` prefix. This is the canonical
   database namespace for the agent business domain.
2. Internal identifiers are `int64`; API serialization is string.
3. `decimal` fields are serialized as strings in APIs.
4. No plaintext secrets in business tables.
5. Soft-delete plus audit trace for management operations.
6. Tenant and organization boundaries are explicit columns, not implicit filters.
7. Runtime business `BIGINT id` values are generated by the unified Snowflake
   ID generator before insert and are bound explicitly in SQL. PostgreSQL DDL
   must define `id BIGINT NOT NULL PRIMARY KEY` and must not use `BIGSERIAL`,
   `GENERATED ... AS IDENTITY`, `nextval`, `RETURNING id`, `MAX(id)+1`, or
   other database-side allocation strategies for runtime business records.
8. Rust implementations use the appbase `sdkwork_id::SnowflakeIdGenerator`
   through the `AgentIdGenerator` SPI wrapper. Business services depend on the
   repository `next_id()` contract, not on database sequences or local counters.

## 3. Table Contracts

### 3.1 `a_agent_business`

Primary business table for managed agents.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | `BIGINT` | N | Internal row id. |
| `uuid` | `VARCHAR(64)` | N | External stable id. |
| `tenant_id` | `BIGINT` | N | Tenant isolation key. |
| `organization_id` | `BIGINT` | N | Organization isolation key, `0` for tenant-level. |
| `owner_user_id` | `BIGINT` | N | Owner user identity id. |
| `agent_id` | `VARCHAR(128)` | N | Stable agent contract id (`AgentManifest.agent_id`). |
| `code` | `VARCHAR(128)` | N | Human-readable stable code within tenant scope. |
| `display_name` | `VARCHAR(255)` | N | Display name. |
| `description` | `TEXT` | Y | Optional business description. |
| `manifest_json` | `TEXT` | N | Canonical agent manifest JSON snapshot. |
| `default_code_task_intent_json` | `TEXT` | Y | Optional default code-task intent snapshot. |
| `implementation_provider_id` | `VARCHAR(128)` | Y | Default implementation provider id selected at agent creation, for example `provider.model.rig-rust`. |
| `implementation_kind` | `VARCHAR(64)` | Y | Implementation kind (`manifest-only`, `typed-local-provider`, `process-adapter`, `protocol-adapter`). |
| `status` | `SMALLINT` | N | Lifecycle status enum (`0 draft`, `1 active`, `2 disabled`, `3 archived`, `4 deleted`). |
| `visibility` | `SMALLINT` | N | Visibility enum (`0 private`, `1 organization`, `2 tenant`, `3 public`). |
| `tags_json` | `TEXT` | N | JSON array of tags. |
| `created_at` | `TIMESTAMP` | N | Creation timestamp (UTC). |
| `updated_at` | `TIMESTAMP` | N | Last update timestamp (UTC). |
| `deleted_at` | `TIMESTAMP` | Y | Soft-delete timestamp (UTC). |
| `version` | `BIGINT` | N | Optimistic concurrency version. |

Constraints:

- PK: `id`
- Unique: `(tenant_id, agent_id)`
- Unique: `(tenant_id, code)`
- Check: `implementation_kind is null or in ('manifest-only','typed-local-provider','process-adapter','protocol-adapter')`
- Check: `implementation_provider_id is null or matches ^provider\.[a-z0-9_-]+(\.[a-z0-9_-]+)*$`
- Check: `status in (0,1,2,3,4)`
- Check: `visibility in (0,1,2,3)`

Indexes:

- `idx_a_agent_business_tenant_org_status_updated` on
  `(tenant_id, organization_id, status, updated_at desc)`
- `idx_a_agent_business_tenant_owner_status` on
  `(tenant_id, owner_user_id, status)`

### 3.2 `a_agent_provider_binding`

Provider implementation binding table for managed agents.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | `BIGINT` | N | Internal row id. |
| `uuid` | `VARCHAR(96)` | N | External stable row id. |
| `tenant_id` | `BIGINT` | N | Tenant isolation key. |
| `agent_id` | `VARCHAR(128)` | N | Stable managed agent id. |
| `binding_id` | `VARCHAR(128)` | N | Stable binding id within an agent. |
| `provider_id` | `VARCHAR(128)` | N | Implementation provider id, for example `provider.model.rig-rust`. |
| `implementation_kind` | `VARCHAR(64)` | N | Implementation kind (`manifest-only`, `typed-local-provider`, `process-adapter`, `protocol-adapter`). |
| `configuration_profile_id` | `VARCHAR(128)` | N | Safe configuration profile id. Secret values are not stored here. |
| `capabilities_json` | `TEXT` | N | JSON array of capability ids exposed by the provider binding. |
| `active` | `BOOLEAN` | N | Whether this binding is the active/default binding for the agent. |
| `version` | `BIGINT` | N | Optimistic concurrency version. |
| `created_at` | `TIMESTAMP` | N | Creation timestamp (UTC). |
| `updated_at` | `TIMESTAMP` | N | Last update timestamp (UTC). |

Constraints:

- PK: `id`
- Unique: `uuid`
- Unique: `(tenant_id, agent_id, binding_id)`
- Partial unique: only one active binding per `(tenant_id, agent_id)`
- Check: `implementation_kind in ('manifest-only','typed-local-provider','process-adapter','protocol-adapter')`
- Check: `binding_id` matches `^binding\.[a-z0-9_-]+(\.[a-z0-9_-]+)*$`
- Check: `provider_id` matches `^provider\.[a-z0-9_-]+(\.[a-z0-9_-]+)*$`
- Check: `configuration_profile_id` matches `^profile\.[a-z0-9_-]+(\.[a-z0-9_-]+)*$`
- Check: `capabilities_json` is a JSON array of unique string capability ids;
  each id is at most 128 characters and matches
  `^[a-z0-9_-]+(\.[a-z0-9_-]+)+$`

Indexes:

- `uk_a_agent_provider_binding_active_default` unique partial index on
  `(tenant_id, agent_id)` where `active = true`
- `idx_a_agent_provider_binding_tenant_agent_updated` on
  `(tenant_id, agent_id, active desc, updated_at desc, binding_id asc)`
- `idx_a_agent_provider_binding_tenant_provider` on
  `(tenant_id, provider_id)`

Rules:

- Updates must use `version` as an optimistic concurrency precondition.
- Activating one binding must deactivate the previous active binding in the same
  tenant and agent scope.
- `configuration_profile_id` identifies a profile; raw secrets are forbidden.
- `binding_id`, `provider_id`, `configuration_profile_id`, and
  `capabilities_json` are validated at service, row-mapping, OpenAPI, and
  PostgreSQL CHECK boundaries.
- Local in-memory repositories used by contract tests must enforce the same
  version and single-active-binding rules as PostgreSQL adapters.
- Provider binding list order is standard: `active desc`, `updated_at desc`,
  `binding_id asc`.

### 3.7 Agent Knowledge Tables

Agent knowledge is the governed business persistence surface for durable
knowledge bases, sources, documents, chunks, retrieval indexes, bindings, and
sync jobs. It is distinct from memory:

- Knowledge is domain/product/document/wiki/reference data retrieved through
  the `KnowledgeProvider` SPI and composed into RAG context by callers.
- Memory is learned agent/user/session state. Memory may cite knowledge through
  `source_kind = knowledge-ref`, but memory is not the standard RAG boundary.
- RAG is provider-neutral and is not vector-only. Standard knowledge index
  kinds are `exact`, `keyword`, `full_text`, `structured`, `graph`, `wiki`,
  `rule`, `vector`, `hybrid`, `llm_rerank`, and `external`.
- Knowledge business rows store safe references, hashes, policy JSON, and
  metadata. Raw credentials, unmanaged embeddings, and plaintext secret
  material are forbidden.
- Active read/list/search/index/binding/sync operations treat soft-deleted
  knowledge bases, sources, documents, chunks, and indexes as unavailable.
  Delete/restore operations may read soft-deleted rows only for lifecycle
  transition checks.
- Parent scope is strict. Sources and documents belong to one knowledge base;
  chunks belong to one document; parent chunks must be in the same document;
  retrieval indexes may be base scoped or document scoped, but chunk-scoped
  indexes must also reference the owning document.

### 3.8 Agent Memory Tables

Agent memory is a governed business persistence surface for agent state,
learned facts, preferences, procedural knowledge, short-lived working context,
episodes, corrections, and summaries. It is related to knowledge/RAG but is not
the same thing:

- Memory records are agent/user/session/domain state learned or curated during
  operation.
- Knowledge records live in agent knowledge bases or external document systems.
- RAG retrieval can combine memory and knowledge. A memory source may reference
  knowledge through `source_kind = knowledge-ref`.
- Retrieval is not limited to vectors. The standard retrieval index kinds are
  `keyword`, `sparse`, `vector`, `graph`, `wiki`, `rule`, and `hybrid`.

## 4. Security And Privacy

1. `manifest_json`, `default_code_task_intent_json`, `capabilities_json`,
   `capabilities_snapshot_json`, schemas, prompt/template content, knowledge
   policy/source/document/chunk/index references, memory policy JSON, memory
   content JSON, evidence JSON, index references, marketplace metadata, and
   `payload_json` must not include secret plaintext or token values.
2. Audit payload is redacted-safe by contract; only safe metadata is persisted.
3. Access must be enforced through tenant + organization + subject policy.
4. Knowledge data must preserve source/document/chunk/index provenance, trust
   level, redaction classification, and retrieval method independence.
5. Memory data must preserve provenance and support redaction/retention flows.
   Retrieval indexes are safe references to local or external indexes, not a
   license to store raw embeddings, secrets, or unmanaged payloads in business
   tables.

## 5. Migration Strategy

Expand-contract sequence:

1. Add new tables and indexes.
2. Wire repository adapters with read/write and policy checks.
3. Backfill any legacy data if required.
4. Enable strict API operations and SDK generation.
5. Add archival/retention jobs after operational baselines are stable.

## 6. Business CRUD Surface

The business service and repository SPI expose type-specific CRUD methods rather
than a generic JSON marketplace item API:

- Skill packages: create, update, get, list, soft-delete, restore.
- MCP servers: create, update, get, list, soft-delete, restore.
- Prompt templates: create, update, get, list, soft-delete, restore.
- Knowledge bases: create, update, get, list, search, soft-delete, restore.
- Knowledge sources: create, update, get, list by knowledge base id, soft-delete, restore.
- Knowledge documents: create, update, read/get, list by knowledge base id, soft-delete, restore.
- Knowledge chunks: create, get, list by document id.
- Knowledge indexes: upsert, get, list by document id, search by knowledge base id.
- Knowledge bindings: create, get, list by knowledge base id.
- Knowledge sync jobs: create, get, list by knowledge base id, start, complete, fail, cancel.
- Memory stores: create, update, get.
- Memory profiles: create, get.
- Memory bindings: create, get.
- Memory namespaces: create, get.
- Memory records: create, get, list by namespace, soft-delete, restore.
- Memory sources: create, list by memory id.
- Memory relations: create, list by memory id.
- Memory retrieval indexes: upsert, list by memory id.

All mutation commands are authorized through `agent.business.manage`, emit
tenant-sensitive audit events, and enforce optimistic concurrency when
`expected_version` is supplied. Skill, MCP, and prompt list queries share a
standard marketplace query: tenant, organization, owner, status, visibility,
search, category, tag, and include-deleted filters. Knowledge document/chunk/
index list queries preserve source, document, chunk, and retrieval provenance.
Knowledge base, source, document, chunk, index, binding, and sync-job
read/list/search paths use active-parent validation and hide soft-deleted parent
resources. Knowledge source update/delete, document update/delete, and sync-job
runtime transition paths also require active parent resources; restore paths
validate parent resources before restoring soft-deleted children. Knowledge
binding scope consistency is enforced: agent scopes require matching
agentId/scopeRef, and deployment scopes require agentId plus matching
deploymentId/scopeRef. Knowledge chunk, index, and binding update/delete/restore
operations are not exposed until the schema adds the required lifecycle,
version, timestamp, and audit semantics. RAG search is provider-neutral and may
use exact, keyword, full-text, structured, graph, wiki, rule, vector, hybrid,
LLM-rerank, or external retrieval; vector metadata is required only for vector
indexes. Memory record list queries are namespace-scoped and hide soft-deleted
records by default. Memory binding scope consistency is enforced: agent scopes
require matching agentId/scopeRef, and deployment scopes require agentId plus
matching deploymentId/scopeRef. Memory profile, binding, record, source,
relation, and retrieval-index create/list/restore paths use active-parent
validation and hide soft-deleted parent resources. Memory retrieval index list
queries are memory-record scoped and support non-vector RAG patterns such as
wiki, rule, graph, keyword, and hybrid retrieval.
